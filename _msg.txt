Confirm before deleting an attachment

The delete icon fired the API immediately. A stray click destroyed a purchase
receipt - the one file in this drawer that cannot be recreated from data, since
nothing else records what was paid for a laptop.

The icon now only opens a ConfirmDialog. handleDelete is reachable solely through
its onConfirm, so there is no path from the button click to the API, and the
confirmation names the consequence ("cannot be undone") rather than asking a bare
"are you sure", which does not tell the user the receipt is gone for good.

FIXING THIS EXPOSED A BUG IN THE SHARED ConfirmDialog, which affected every
destructive dialog in the app.

Radix's AlertDialogAction closes the dialog itself on click, before the action's
promise settles. A FAILED action therefore closed the dialog with no message -
the dialog vanishing reads exactly like success, which is the precise failure
mode the `error` prop was added for. Guarding onOpenChange against `loading` does
not fix it either: `loading` only becomes true after React re-renders, and Radix
has already fired its close by then.

So the semantics are now "close when the action RESOLVES". The click's default is
prevented and the result awaited: fulfilled closes, rejected leaves the dialog open
with the error visible. A synchronous onConfirm still closes immediately, so no
existing caller changes behaviour.

Checked every ConfirmDialog consumer for the consequences. Exactly one returns a
real promise - asset-categories, via mutateAsync - and it already passes `error`,
so it now correctly stays open on failure instead of vanishing. The rest pass
block-bodied or mutate() callbacks that return undefined and are unaffected.

One more trap worth recording: the card passed `onConfirm={() => void handleDelete()}`.
The `void` DISCARDS the promise, so the new check saw undefined, concluded
"nothing to await", and closed immediately - reproducing the original bug exactly.
The callback now returns the promise, and handleDelete re-throws after setting the
message, because a swallowed rejection also reads as success.

Three tests: the click reaches no API and the confirmation appears; Escape cancels
and deletes nothing; a failed delete keeps the dialog open with an explanation.
Verified they fail when the confirmation is bypassed.
